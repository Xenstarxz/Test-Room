สรุปสิ่งที่ต้องแก้/เพิ่ม เพื่อเปลี่ยนจาก "Max = เพดานต่อการจอง 1 ครั้ง" ให้กลายเป็นระบบสต็อกรวมจริงที่หมุนเวียนตามช่วงเวลา เหมือนกับการเช็คห้องว่าง

00 Logic ที่ยืนยันแล้ว

สต็อกเช็คแบบ "ทับซ้อนช่วงเวลา" — ไม่ใช่ลดถาวร

สต็อกอุปกรณ์คืนกลับมาเองตามช่วงเวลา เหมือนเช็คห้องว่าง ไม่ใช่ตัดออกจากคลังแบบถาวร

คำนวณจาก booking ที่ยัง active (ไม่ cancelled) และช่วงเวลาทับซ้อนกันเท่านั้น — ไม่ใช่ทั้งวัน

ตัวอย่าง: ไมค์มีสต็อกรวม 4 ตัว

OK ห้อง A จองไมค์ 2 ตัว — วันจันทร์ 08:00–09:00 → ผ่าน (สต็อกเหลือ 2 ตัวในช่วงนี้)
BLOCK ห้อง B จองไมค์ 3 ตัว — วันจันทร์ 08:00–09:00 (ทับซ้อนกับ A) → เกินสต็อกที่เหลือ (มีแค่ 2) ต้องเตือน
OK ห้อง C จองไมค์ 3 ตัว — วันจันทร์ 13:00–14:00 (คนละช่วงเวลา ไม่ทับซ้อนกับ A) → ผ่านปกติ เพราะสต็อกเต็ม 4 ตัวในช่วงนี้ 
สต็อกที่เหลือ(อุปกรณ์ X, ช่วงเวลา T)
  = สต็อกรวม(X)
  − ผลรวมจำนวน X ที่ถูกจองไปแล้วใน booking ที่ยัง active (ไม่ cancelled)
    และช่วงเวลาทับซ้อนกับ T (start < b.end && end > b.start)

01 ไฟล์ที่ต้องแก้/เพิ่ม

เรียงตามลำดับที่ควรทำ — backend ก่อน แล้วค่อย UI

แก้ของเดิม server/routes/settings.js

เพิ่มฟิลด์ equipment_stock (สต็อกรวมทั้งองค์กร) แยกจาก equipment_limits.max (โควตาต่อการจอง) ที่มีอยู่แล้ว — เป็นคนละความหมายกัน ห้ามรวมเป็นตัวเดียว

  • โครงสร้างใหม่: equipment_stock: { 'ไมค์': 4, 'พอยเตอร์': 2, ... }
  • เพิ่มใน getAllSettings() และ endpoint PUT / ให้แอดมินแก้ได้
แก้ — สำคัญที่สุด server/routes/bookings.js

เพิ่มฟังก์ชันเช็คสต็อกคงเหลือ ก่อน insert/update booking ทุกจุด ใช้ pattern เดียวกับ findConflicts() ที่เช็คห้องว่างอยู่แล้ว

  • ต้องเพิ่มใน 3 endpoint ให้ครบ — จุดเดียวกับที่เคยพลาดตอนเช็ค room.status === 'maintenance' ไม่ครบมาก่อน:
    • POST /bookings (จองปกติ)
    • PATCH /bookings/:id (แก้ไขการจอง)
    • POST /bookings/recurring (จองซ้ำรายสัปดาห์)
  • ห่อด้วย db.transaction() เหมือนที่แก้ race condition ของห้องไปแล้ว — กัน 2 คนจองพร้อมกันในช่วงเวลาเดียวกันจนเกินสต็อกจริง
  • Error message ควรบอกว่าเหลือกี่ตัว เช่น "ไมค์เหลือ 2 ตัวในช่วงเวลานี้ (ขอ 3 ตัว)"
แก้ของเดิม src/components/booking/BookingModal.jsx

ส่วน stepper อุปกรณ์ที่มีอยู่แล้ว (การ์ด + ปุ่ม +/− ต่ออุปกรณ์) ต้องโชว์ "เหลือ X ตัวในช่วงเวลานี้" แบบ real-time ตามวันที่/เวลาที่ผู้ใช้เลือกอยู่ในฟอร์ม ไม่ใช่แค่โชว์ Max คงที่แบบเดิม

  • เรียก API เช็คสต็อกคงเหลือทุกครั้งที่ผู้ใช้เปลี่ยนวันที่/ช่วงเวลาใน modal
  • ถ้าสต็อกเหลือน้อยกว่า Max เดิม (เช่น Max ต่อครั้ง 4 แต่เหลือแค่ 2) ต้อง clamp ปุ่ม +/− ไม่ให้กดเกิน 2
หน้าตั้งค่า หน้า "กำหนดโควตา Min/Max ของแต่ละอุปกรณ์" (ตามภาพ)

เพิ่มอีก 1 ช่องต่ออุปกรณ์ 1 ชนิด แยกจากช่อง Max เดิม

  • ช่องเดิม: "Max (สูงสุด)" = โควตาต่อการจอง 1 ครั้ง (ของเดิม ไม่เปลี่ยน)
  • ช่องใหม่: "สต็อกรวม" = จำนวนของจริงที่มีทั้งองค์กร

02 ลำดับที่แนะนำให้ทำ

1. เพิ่ม equipment_stock ใน settings.js

ฐานข้อมูล + API ก่อน ยังไม่ต้องผูกกับ booking logic

2. เขียนฟังก์ชันเช็คสต็อกคงเหลือ (แยกไฟล์ใหม่ได้ เช่น server/utils/equipment.js)

รับ (อุปกรณ์, วันที่, ช่วงเวลา, exclude bookingId ตอน edit) → return จำนวนคงเหลือ ใช้ pattern เดียวกับ findConflicts()

3. ผูกเข้า 3 endpoint ใน bookings.js พร้อม transaction

จุดสำคัญที่สุด ต้องทดสอบให้ครบทั้ง 3 endpoint ไม่ใช่แค่ endpoint เดียว

4. เพิ่ม endpoint เช็คสต็อกคงเหลือแบบ real-time สำหรับ frontend

เช่น GET /api/equipment/availability?date=...&start=...&end=... ให้ modal เรียกใช้

5. อัปเดต BookingModal.jsx ให้โชว์สต็อกคงเหลือ real-time

ทำหลังสุดเพราะต้องมี endpoint จากข้อ 4 ก่อน

6. เพิ่มช่อง "สต็อกรวม" ในหน้าตั้งค่า (ตามภาพ)

ทำคู่ขนานกับข้อ 1 ได้เลย เป็นแค่ UI form เพิ่ม

ข้อควรระวัง: ห้ามลืมใส่เช็คสต็อกใน endpoint ใดจาก 3 ตัว (create / update / recurring) เพราะจะเปิดช่องให้จองอุปกรณ์เกินสต็อกจริงผ่าน endpoint ที่ลืมเช็ค — เป็น pattern บัคเดียวกับที่เคยเจอตอนเช็คห้องปิดปรับปรุงไม่ครบทุก endpoint มาก่อน ต้องทดสอบยิง API ตรงๆ ทั้ง 3 endpoint แยกกัน ไม่ใช่เทสผ่าน UI อย่างเดียว
สรุปจาก requirement ที่ยืนยันร่วมกันในบทสนทนา — ยังไม่มีการแก้ไขไฟล์โค้ดจริงในเอกสารนี้ เป็นแผนงาน (spec) เท่านั้น
